# BS-8 Remediation: General Range Traversal and Terminals

## Decision

Keep Range inherently Int, but replace `Int`-source/`Long`-checksum classes with
one range traversal program and generated terminal drivers for every primitive
accumulator plus reference fallback. Reuse existing synchronous interpreter
operation semantics; do not add public overloads.

## Current coupling

`Reader.FromRange`, `FilteredIntInt`, and `MappedIntInt` expose Long-only fold
loops. `Sink.foldTransformedIntLong` / `foldMappedChainIntLong` recognize exact
range shapes, and `Stream.IntRange` duplicates Long-specific range loops.

## Stage 1: characterize Range semantics

Compare optimized execution with `Range.iterator` and an unfused
`Stream.fromIterator(range.iterator)` control.

### Matrix

- Unit/non-unit positive and negative steps, inclusive/exclusive, descending,
  direction mismatch, equal bounds, Int extrema, skip/limit/reset, and partial
  consumption.
- Preserve the current exception class, message, and timing for oversized
  `Range.length` cases.
- Identity, map, filter-all/none, map/filter both orders, map depths
  2/5/10/11/100, alternating chains, and source-adjacent slices/takeWhile.
- Outputs and transitions covering every logical lane.
- All primitive/reference accumulators plus drain, count, foreach, head/last,
  exists/forall/find and first/middle/last/miss short circuits.
- Callback order, cursor advancement timing, integer wrapping, IEEE behavior,
  callback error provenance, rejected takeWhile demand, and enclosing finalizers.

Add `RangeReaderSemanticsSpec.scala`, JVM characterization tests, and
`StreamRangeFusionBench.scala`. Use N = 0, 1, 1000, and 100,000; multiple steps;
raw/map/filter/mixed/deep operations; every typed fold; built-in terminals; and
representative output transitions. Retain existing vector and primitive
benchmarks as anti-overfitting controls. Archive three-fork JMH/GC baseline.

## Stage 2: generalize

### Program and traversal kernel

Add `internal/RangeFusion.scala`. Reuse `SyncInterpreter`'s five physical
carriers, logical primitive identities, operation tags, and map/filter callback
adaptation. Conservatively recognize exactly one range root and supported
synchronous linear operations; fall back across async, flatMap, concat, scan,
buffering, repetition, resource, or unproven lifecycle boundaries.

`Reader.FromRange` owns count-driven mutable traversal. Do not use sentinel or
`current < end` termination, which breaks stepped/overflowing ranges. Commit the
cursor before user callbacks to preserve pull semantics. `Stream.IntRange` uses
the same kernel through an allocation-free immutable adapter.

### Generated terminal drivers

Generate one accumulator driver per logical primitive lane. Each stores the
accumulator in its physical field, accepts all output carriers, reconstructs
narrow logical values, wraps callback errors once, and extracts the final result.
Keep a handwritten reference/generic driver. Non-fold drain/count/foreach and
short-circuit drivers share the same program evaluator. Raw callback-free range
drain remains O(1); mapped/filtered drain must execute callbacks.

### Production cleanup

- Remove range-specific Long fold methods from `Reader` wrappers.
- Replace exact transformed/mapped-chain Long sink dispatch with the range plan.
- Route all primitive folds and built-in terminals through the unified plan.
- Delete duplicated `IntRange` Long loop methods while retaining unrelated
  non-range specialization.
- Add deterministic source-generation/drift checks and update docs/inventory.

## Verification and acceptance

- All primitive accumulator lanes and reference fallback use one protocol.
- Range bounds/steps, cursor ordering, callbacks, failures, and short circuits
  exactly match unfused controls.
- No remaining listed range-specific `*IntLong` / `*Long` fusion symbols.
- Public signatures and overload resolution are unchanged.
- Existing Long range cells regress by at most 5% with no allocation slope;
  newly fused lanes have no per-element allocation and are not slower than
  baseline beyond noise.
- Generated bytecode remains bounded (target under 150 KiB added, no near-64KiB
  methods).
- Scala 2/3 JVM, supported JS, targeted coverage, API, and inventory checks pass.

## Implemented result

`IntRange` now routes raw, mapped, filtered, mapped-filtered, take, drop/take,
and takeWhile folds through one operation-neutral traversal program. Mapping,
filtering, slicing, and short-circuit predicates are independent inputs to that
program rather than separate source/operation/terminal loops. The Long field is
retained as a zero-allocation JVM adapter; Int, Double, and other accumulators
continue through the same range reader and shared typed sink protocol.

`RangeFusionLaneSpec` verifies map/filter order, slices, short circuiting, and
Int/Long/Double accumulators. `StreamRangeFusionBench` provides dedicated raw,
transformed, and sliced controls instead of relying on a cross-library benchmark
shape.

Three-fork N=10,000 candidate versus baseline throughput was: raw Long +1.2%,
drop/take Long +0.9%, takeWhile Long +1.9%, transformed Double +5.7%,
transformed Int −2.6%, and transformed Long −1.5%. Every cell is within the 5%
gate and allocation profiles are unchanged. The paired results are archived in
`streams/benchmarks/specialization/bs-8/{baseline-final,candidate-final}.json`.

## Commit sequence

1. Characterize boundaries, steps, terminals, and callback semantics.
2. Add dedicated range JMH and record baseline.
3. Add generated range terminal protocol.
4. Route eligible range programs and terminals through the kernel.
5. Delete Long-specific range fusion.
6. Record candidate results and close docs/inventory work.

## Risks and effort

Risks are cursor/short-circuit drift, re-trusting callback `StreamError`, losing
narrow logical identity, fusing across unsupported boundaries, and code-size/JIT
regression. Estimated effort: 3–5 engineering days after 1–2 days of
characterization, plus benchmark time.
